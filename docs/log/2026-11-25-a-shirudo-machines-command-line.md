*Why:* a machine that runs shirudo needs more than integrity (#734): without `bpf.keyring_unsealed=1` and `dm_verity.keyring_unsealed=1` the kernel seals the `.bpf` and `.dm-verity` keyrings empty at boot (kernel/bpf/keys.c, drivers/md/dm-verity-verify-sig.c), and shirudo's init cannot enroll its certificates (#741). *Done:* `Cmdline.LockdownIntegrity` is now `Cmdline.Lockdown`, a `machine.Lockdown` (spin-machine's `--lockdown`) with three values, so integrity without the keyrings and unsealed keyrings at confidentiality cannot be asked for: `LockdownConfidentiality`, the zero value, `lockdown=confidentiality` with both keyrings sealed; `LockdownShirudo`, no `lockdown=` and both keyrings unsealed; `LockdownKernel`, nothing, for the lab's traceable kernel. That kernel's boots pass `--lockdown=kernel` and not shirudo's: nothing in a traced boot enrolls a key, and an unsealed `.bpf` keyring has the verifier refuse a signed program its caller's own keyring. `Args` refuses a `lockdown=` or either keyring parameter in `Extra`, dashes read as underscores as the kernel reads them. The choice is the booted guest's and not in the machine's record: a checkpoint resumes the guest it saved. `task boot:lockdown` boots one guest of each and adds a key to each keyring from inside it (keyring-probe), which a sealed one refuses: on a tree of v20261124.01 with this checkout's kernel (laptop, 2026-11-25), confidentiality read `none integrity [confidentiality]` with both sealed, shirudo `none [integrity] confidentiality` with both open, the kernel's `none [integrity] confidentiality` with both sealed. A kernel before 7.4 has neither keyring, which the check accepts until a release carries 7.4 (#738). *Status:* every workspace keeps confidentiality and sealed keyrings; spin asks for a shirudo machine when it runs shirudo in one.
