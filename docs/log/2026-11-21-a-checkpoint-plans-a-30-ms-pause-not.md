The phases showed a 1.6 GiB checkpoint's guest stopping with 0.3-0.9 GiB still to write, and that remainder was most of `Cost.Paused`. *Explained:* QEMU stops the guest once what is left fits in `downtime-limit` times the rate it measured over the last 100 ms. The machine never set the limit, so it was the default 300 ms. Into the page cache the rate read 30-34 Gbit/s, so the guest stopped with up to ~1.2 GB to go. An idle guest stopped part-way through QEMU's first pass, and what was written after the stop was memory QEMU had not reached yet, not memory the guest had dirtied. Mapped-ram, multifd and pause-before-switchover leave that test as it is (QEMU 11.2's `migration/migration.c`). *Measured* (bench, nested KVM, v20261121.01, spin's shape plugged to 2 GiB, 20 saves an arm interleaved on one guest, branch `exp/415-downtime`): at 30 ms QEMU's downtime fell from 192 ms to 6 for an idle guest with 1.5 GiB of tmpfs filled, −186 [−189, −184], and the save's total did not move, +4 [−2, +6]. With a writer rewriting 64 MiB of a 512 MiB set every ~100 ms it fell from 221 ms to 8, −213 [−218, −208]. The total rose 39 ms [+33, +45] for one more pass and 195 MiB more written while the guest ran. The laptop agreed, at 238 to 12 and 209 to 11. A writer rewriting 256 MiB of a 1 GiB set with no pause converged at 30 ms in all 10 saves (laptop). *Rejected:* 100 ms (60 ms of downtime with the writer, laptop); auto-converge, whose throttle never engaged in any save; `avail-switchover-bandwidth`, not run, since it only stands in for the rate in the same test. *Found on the way:* `cont` right after `Checkpoint` once failed with "Migration is not finalized yet", because QEMU sends `completed` before it moves the run state to `postmigrate`. That is #421. *Status:* in place. A checkpoint is on neither goal clock, and `Resume` reads the same file, so restore-first was not re-run. boot:record resumed a checkpoint saved at 30 ms.
