Checkpoint, Resume and Loaded asked `query-migrate` every millisecond until the migration reached the state they waited for. They now turn on the `events` capability with the others they set, arm a `qmp.Expect` for `MIGRATION` before the command that moves the migration, and wait on it. `query-migrate` is asked only after a save that failed, for its reason. *What QEMU 11.2.0-rc0 sends* (`TestACheckpointIsWaitedOnByItsEvents`, in `boot:record`, laptop and bench): a save sends setup, active, `STOP`, pre-switchover, device, completed. A full load sends setup, active, `RESUME`, completed, so the guest runs before the event. A fast load sends setup, active, postcopy-device, postcopy-active, `RESUME`, completed (bench only, where the runner turns userfaultfd on), so `Resume` returns before the guest runs, as it did when it polled. Half a state sends setup, active, failed, and QEMU exits (migrate-incoming's exit-on-error) with the reason on its stderr. A `query-migrate` after that event found the connection reset, so a failed load asks nothing and says where the reason is. *Measured* on the bench, spin's shape and login, 20 each interleaved, v20261120.04 with its own spin-machine against the same tree with this branch's (which also carries the record, the module rename and the public QMP client): restore-first's first login −0.4 [−2.9, +0.8] evicted and −1.4 [−3.2, +0.8] cached, running −0.3 [−1.8, +0.7] and −0.7 [−1.7, +0.3], all within noise (lab 44898581478). ssh-first's first login +0.9 [−5.4, +5.3], sshd accepts −0.2 [−5.1, +5.2], within noise; the console prompt read +6.1 [+0.3, +9.0], a diagnostic on a path this change does not touch (a cold boot waits on no migration), left for the next release's record to confirm or not (lab 44898910862).
