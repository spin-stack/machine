*Why:* 0012, parsing vmlinux BTF on first use instead of at the first kfunc registration (11-22, archived as `archive/exp-btf-first-use`), took 7 ms out of the kernel and put it into journald's start, because `bpf_check()` asked for the BTF for every program, journald's cgroup device and skb programs (`DeviceAllow=`, `IPAddressDeny=`) among them. *Changed:* 0012 as measured, and 0013, which has the verifier ask for the BTF only where a kernel type first enters a program: a program with its own BTF or a BTF-typed attach point, the first kfunc call, a vmlinux BTF id in ld_imm64, a map pointer access, a helper argument or return typed by vmlinux BTF, `bpf_find_vma()`'s callback, and `bpf_snprintf_btf()` / `bpf_seq_printf_btf()`. Prior art: Jay Wang's bpf-next series of 2026-09-23 (LWN 1096093, not merged) chose the same points; the eager fetch came with 8580ac9404f6 (2019). *Reviewed* (an independent read of both patches, every `btf_vmlinux` reader in kernel/bpf): two bugs found and fixed before the patch was carried. The printf-BTF helpers read the BTF as the program runs, in atomic or NMI context, and with no trigger at load they could have started the parse there; they now ask for it at load. A parse that failed for memory in whichever task asked first (an unprivileged bpffs mount's `delegate_*` options can choose that task) latched the error for the whole boot; it is now tried again by the next user, and only a malformed BTF is final. vmlinux BTF now has no object id until it is parsed. *Measured* (bench, nested, spin's shape and login, against v20261123.04): no exit moves (3 a side, lab 45113437048). The first login −10.0 [−12.7, −3.3] at 60 a side and −6.3 [−9.1, −4.6] at 120 before the fixes; the kernel carried −6.4 [−9.4, −1.0] at 60, sshd accepting −6.7 [−9.5, −2.2]. Restored −1.0 [−6.0, +4.2] evicted and +1.7 [−9.1, +10.2] cached, 30 a side, the state 1.3 MiB smaller (the BTF is not in it). The build asserts both (kernel/README.md). *Status:* in place; reaches the goal number with the next release.
