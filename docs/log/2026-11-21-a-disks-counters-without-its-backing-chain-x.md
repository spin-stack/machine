The question was whether a runner polling `Process.Usage` across ~20 machines, and the watch's read of a held disk each second, slow the machines. #402 said `query-blockstats` cost ~6 ms p50 "because every reply carries all 16 hotplug slots", and that one took 536 ms under host steal. *Explained* (laptop, spin's shape, the command timed beside query-status with QEMU's main thread's `schedstat` across each call). The hotplug targets are not in the reply, since an empty SCSI target has no block backend. What is in it is every image of each disk's backing chain, twice under a place's throttle filter (`bdrv_query_bds_stats` recurses into `parent` and `backing`). The reply was 12.6 KiB for a root of an overlay over the base plus a raw home. Each image added ~3.6 KiB and ~70 µs of the main loop, which also runs the disks' I/O: 0.37 ms of main loop at depth 1, 0.73 at 8 and 2.5 ms (124 KiB) at 32. Every seal of a workspace's disk adds an image. The 6 ms is a deep chain or a loaded host, not the slots. *The 536 ms is not the command.* Each call over 50 ms in the pressure probe's lane, sampled every 0.5 ms, had QEMU stalled in the host. At `memory.high` the main thread was in D state in its cgroup's reclaim (`reclaim_high` → swap writeout → `wbt_wait`) or a swap-in, for 170-195 ms, and query-status was as slow. In the memory and OOM phases it was in `mmap` waiting for the mmap lock while the vCPU faulted, 52-284 ms. Under `cpu.max` the monitor's thread was throttled for 80 ms. Two busy loops on QEMU's core cost a call 4-6 ms at most. A first run that traced QEMU to a file on ext4 caught its threads in the trace's own `writev`, so a stall measured with tracing to a busy disk can be the trace. *Built:* `qemu/patches/0004` adds `query-blockstats`' member `x-flat`, which leaves out `parent` and `backing`. `QEMU.DiskUsage`, Usage's QMP half and what the watch reads, asks with it. A QEMU without it (every release up to v20261121.01) refuses the member, so it is asked once and then only without it. The `usage` probe times DiskUsage on a running machine, quiet and pinned to one host CPU beside two busy loops, at a `depth`. *Measured* (bench, nested, spin's shape, v20261122.01 with QEMU from parts run 44972755256, 20 machines each × 200 calls): DiskUsage's main-loop time went from 293 to 96 µs p50, −197 [−202, −181], and its round trip from 573 to 390, −183 [−190, −158] (lab 44973302743). At depth 32 it went from 2991 to 94 µs, −2898 [−2917, −2895], and the round trip from 3377 to 391 (lab 44973302685). Against main's own parts build without 0004, depth 1 read −183 [−203, −176] µs, with query-status +8.1 [−55.5, +39.1] µs, within noise (lab 44973726633). So the +43 µs query-status read against the release is the build, not the patch. *Not explained:* pinned beside two busy loops, DiskUsage's p50 sat at 3.07 ms in every flat run against 2.2 at depth 1 and 4.3 at depth 32 without x-flat, and the slowest call did not change at depth 1. The 3 ms is about one scheduler slice on these hosts (#442). *Not built:* asking only for the held disks. With x-flat, each device costs ~20 µs of main loop (laptop, 2 against 11 places), so the ceiling is ~20 µs a second at spin's shape with one disk held. *Goal numbers:* untouched. DiskUsage has two callers, `Usage`, which spin calls when it chooses, and the watch, which asks only while a disk is held. Neither runs on a boot or a restore. 0004 changes only that command's handler and its HMP caller. boot:record passes on the patched QEMU (lab 44973302762, and on the laptop), and so does boot:pressure on the laptop. *Status:* in place.
