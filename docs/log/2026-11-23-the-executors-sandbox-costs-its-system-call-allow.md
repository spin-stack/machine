#637 split #574's bound and asked for one seccomp filter per unit. *The split* (bench, nested, spin's shape and login, v20261123.06, 60 a side, branch `exp/637-split`, tag `archive/exp-637`): the seccomp settings emptied in journald, logind and `user@` read first login −12.0 [−21.8, −2.1], sshd accepting −13.8 [−19.4, −4.9]; the namespace ones (`ProtectSystem=`, `ProtectHome=`, `ProtectControlGroups=`, `ProtectKernelTunables=`, `ProtectProc=`) +0.3 [−9.4, +7.2] (lab 45228294512). *Fewer filters:* the executor applies `SystemCallArchitectures=` after seven other settings, so each of those loads a filter for i386 and x32 too, which the architecture filter then kills; the kernel has neither ABI. Applied first, journald carries 8 filters, not 17, and logind 13, not 26. `boot:seccomp` (on the tag) runs a probe as each unit's `ExecStartPost=`, with the unit's sandbox, over 3435 calls: every native number with zero arguments and no capabilities, each x32 number, and the calls the settings decide by argument; the table was the release's (labs 45235103665, 45235485857). First login −0.4 [−6.1, +2.7] against systemd rebuilt with a comment only (lab 45231419187). *Where it goes:* an instrument patch timing the executor's steps (thread CPU, one boot, 2 vCPUs): journald's executor 6.7-7.2 ms, `SystemCallFilter=@system-service` 3.7-4.0 of it, its `seccomp_load()` 1.1-1.2; the other seccomp settings ~0.6 together (labs 45238003981, 45239372741). So one filter per unit would reach about the 0.6 ms (inferred). *Found on the way:* the lab's packages edit gave `/usr` the package's mtime, newer than the image's update stamps (#513), so every `--systemd` tree ran ldconfig, sysusers, the hwdb and the catalog before the login: both arms ~658 ms (lab 45229454155); fixed in #673. *Status:* rejected, #637 closed; building the allow-list once is #686.
