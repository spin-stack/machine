`machine.QEMU` gains `CPUs`, `Status`, `Hold`, `Shutdown`, `Done`, `End` and `GuestMemory`. `Memory` returns `MemorySize{Now, Base, Ceiling, Block}`, and `Checkpoint` returns the save's `Cost{Paused, Total, RAM}` from one `query-migrate` after it completes. `VM` gains `CPUs` and the two new returns. The balloon gets an id, `balloon0`, so that `GuestMemory` reads it at a fixed path. It turns the guest's reports on at its first call, so no timer runs in a boot that never asks. *The record:* a held machine of spin's shape read the same 34170 bytes of record with and without the id (laptop, v20261120.04, `spin-machine target` from each build), because the record leaves every id out and names the balloon by its slot. *Shutdown, decided by observation:* spin's runner pressed ctrl-alt-del and pressed the power button only if QEMU refused the keys. QEMU takes them, and the guest never sees them: its kernel has no i8042 or AT keyboard driver. Booted to systemd, a machine sent the keys ran until it was killed (SHUTDOWN host-signal), and one whose power button was pressed powered off 0.64 s later (SHUTDOWN guest-shutdown). So `Shutdown` presses the button alone. *What `End` says* (`TestTheMachineSaysHowItEnded`, in `boot:record`): `poweroff -f` ends as {guest, guest-shutdown}, `Shutdown` under systemd as {guest, guest-shutdown}, and a panic as {guest, guest-reset}, since `panic=1` reboots and `-no-reboot` ends the reboot. No panic device exists, so `GUEST_PANICKED` is never sent. A checkpoint of a 128 MiB guest at the `/bin/sh` prompt cost a 5 ms pause, 56 ms in all and 86 MiB of RAM written. No goal path changes timing: `Boot` and `Resume` send what they sent, and the cost's round trip is on the save, before either clock. *Status:* in place; no checkpoint is refused.
