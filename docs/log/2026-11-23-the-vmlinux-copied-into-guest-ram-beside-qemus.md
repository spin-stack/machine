*Why:* since #645 QEMU loads the vmlinux through `load_elf`. #698 asked whether it read the 40 MB file into ROM blobs at start, as `x86_load_linux` read a bzImage before 0007. It does not: `load_elf` has mapped the file since QEMU 4.2 (816b9fe450, Garzarella, 2019), and the blobs point into the mapping. What it does is copy the 37.4 MB of segments into guest RAM at the machine's first reset, on the main thread, before the main loop answers the monitor. *The phase,* a probe that traces QEMU's reset (`romcopy`, branch `exp/698-romcopy`, never merged): 9.1 ms p50, p95 9.3, 20 boots, bench, spin's shape (lab 45257214350); the ledger read the vmlinux's QEMU start +8.4 against a bzImage's (lab 45260129735, #697). On a laptop half the copy is faulting in the destination's huge pages and half the copy, and a `pread` into guest RAM was no faster than the mapping's `memcpy`, so no cheaper copy was built. *Carried:* QEMU 0009 copies the segments in a thread at the first reset and waits for it before the vCPUs start, a migration's setup, the next reset and QEMU's exit; a machine made for an incoming migration copies nothing at reset, as before. *Measured* (bench, spin's shape and login, v20261123.07 against the same release with 0009's QEMU, interleaved): first login 351 → 342, −8.6 [−11.0, −4.0], sshd accepting −9.1 [−12.4, −5.9], the console prompt −7.7 [−11.4, −5.5], QEMU's RSS unmoved, 60 a side (lab 45260098299); restored −0.1 [−1.1, +0.7] evicted, −0.3 [−2.1, +0.9] cached, the state unmoved, the same run's cold login −6.9 [−12.9, −0.8], 40 a side (lab 45260694485). The gain is the whole traced copy. The record does not move: the patch adds no device, property or RAM block, and `boot:record` passed on the patched tree (lab 45261567066). A stub ELF whose notes have `p_align` 0 kills QEMU 11.2 with SIGFPE in `load_elf`, found while writing the build check (#705, not affected). *Status:* kept.
