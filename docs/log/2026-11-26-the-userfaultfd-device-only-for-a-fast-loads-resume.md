*Why:* `Start` opened `/dev/userfaultfd` for every machine held for a restore, before anyone knew whether its state would load fast, and QEMU kept a descriptor of it from its first userfaultfd to its exit, so removing the set would not have taken it back. A second open in `loadsFast` decided the fast load, so a device that opened there and not in `Start` chose a fast load for a QEMU with no device. *Done:* qemu/patches/0010 opens the device `-userfaultfd` names for each userfaultfd and closes it, with no fallback to the system call (the build's check asks again after `remove-fd` and wants ENOENT). `Resume` opens the device only for a state that loads fast, hands it with `add-fd` in the set every restore's command line names (`userfaultfdSet`), and removes the set at postcopy-active, once QEMU has made its userfaultfd. A failed resume removes it before returning. The device in hand is the fast load: no device, a load in full. `Spec.UserfaultFDSet` is gone, and `ReadAhead` opens nothing. boot:record reads QEMU's descriptors: none of the device while held, after `Resume` in full or fast, or once loaded. QEMU closes postcopy's userfaultfd from a BH after it says completed, so that one is waited for. *Measured* on the bench, spin's shape and login, the base commit's spin-machine and the release's QEMU against this branch's with its QEMU (parts run 45885575364). A fast restore, touched=1700, 30 a side: login −7.8 [−38.7, +24.9] evicted and +3.5 [−16.9, +17.8] cached, running +0.1 [−0.8, +0.9] and +0.6 [−0.4, +2.8], within noise (lab 45888553535). The first try, taking the device back after RESUME, read running +1.6 [+0.4, +2.8] cached at 20 a side (lab 45886134311), one more round trip before `Resume` returned, which moved to postcopy-active. A restore in full, 20 a side: login +0.4 [−1.2, +2.8] and −0.1 [−1.8, +1.4] (lab 45886134494). That run's cached cold login read +6.9 [+1.2, +14.8], where its evicted row's same boot read +1.1. ssh-first at 40 a side read first login +1.4 [−3.3, +5.7], within noise (lab 45886662802), so the cold first login does not move. *Status:* in place. spin needs no code change; its `fastLoadRefusal` comment should say `Resume` instead of `Start`.
