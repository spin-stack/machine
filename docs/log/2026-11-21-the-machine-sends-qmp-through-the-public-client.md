title: the machine sends QMP through the public client, each command defined once (this change)
---
`machine.QEMU` runs on `*qmp.Client`, and machine/qmp.go, the third QMP client after spin's two, is deleted. Every command the machine sends is a `qmpdef.Define`d value beside the code that sends it, and the block and descriptor commands spin's storage agent also sends are public in qmp/block.go. `spin-machine-dev verify qemu` holds all of them to the binary's query-qmp-schema, which refused the record's `query-kvm`: QEMU 11.2.0-rc0 deprecates it. The accelerator is read from `query-accelerators`, whose `enabled` is the accelerator's name, `kvm` or `tcg` for every machine `Spec.Args` starts, so the record's part stays `{"accel", "kvm"}` or `{"accel", "tcg"}`. The version comes from the monitor's greeting, which is query-version's answer, so a record is 7 round trips. *Measured* (laptop, v20261120.04 with QEMU 11.2.0-rc0, spin's shape, `spin-machine` built before and after): the record of a running machine and of one held for a checkpoint are byte-identical under KVM and under TCG, a checkpoint saved by the old `spin-machine` restores with the new one (`restore --target`), and boot:record passes. A round trip costs more through the client: query-memory-size-summary's p50 went from 216 to 263 µs, +47 [+44, +49], and in a second run from 136 to 159, +23 [+21, +27] (laptop under load, one held machine of spin's shape, the old and new client in turn, 6000 and 4500 each). What it pays for is the reader waking the waiting call on another thread: the same client under GOMAXPROCS=1 read 106 µs, below the old client. The record's read moved −0.4 ms [−2.6, +1.7] with one round trip fewer. A restore sends ~20 commands before QEMU loads its state, so 0.5-1 ms more on restore-first is expected (inferred, under the bench's noise at 20 boots). The query-migrate polls stay; events replace them in a change of their own, interleaved against the release on the bench, which decides both. *Status:* in place; no checkpoint is stranded.
