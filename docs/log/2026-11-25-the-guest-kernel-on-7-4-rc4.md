*Why:* shirudo needs the BPF signed loader's ABI (`KEY_SPEC_BPF_KEYRING`, `bpf.keyring_unsealed`, the `bpf_inode_init_xattr` kfunc) and `KEY_SPEC_DM_VERITY_KEYRING`, which 7.3.6 lacks and 7.4-rc4 has, with ML-DSA (`CONFIG_CRYPTO_MLDSA`) to build and the x86 ftrace fix 31ac959c915c already in (#720). Backporting the loader's series onto 7.3 was the other way; the maintainer chose the release candidate, the smaller change. *Done:* the pin is torvalds' 7.4-rc4 tarball from git.kernel.org, which kernel/Dockerfile already fetched for an -rc, and versions.yaml's source says the same; `gates/pins_test.go` now fails a kernel source that is not the tarball the build fetches. `KernelSeries` reads 7.4-rc4 as the series 7.4, and the CVE scan reads it as after every 7.3 and before 7.4.0. Of the 21 patches, 19 applied as they were and 0003 and 0013 are forward-ported, each saying how; every effect check holds, and sparse finds no warning the patches add. The configuration is the series' config-7.4-x86_64, as the builder's olddefconfig writes it: what it dropped from 7.3's file was what olddefconfig no longer derives (VT_CONSOLE without VT, THP_SWAP without THP) or what 7.4 folded in (PROC_SYSCTL into SYSCTL, PER_VMA_LOCK made unconditional). Reading that diff found /dev/port in every release so far: 7.3's file had no DEVPORT line, and olddefconfig turned it on from its default (v20261124.01's kernel-config says `CONFIG_DEVPORT=y`). Lockdown refused opening it (LOCKDOWN_DEV_MEM), as it refuses ioperm and iopl; it is now off with DEVMEM and PROC_KCORE, and the build checks it. The build also fails now when olddefconfig changes the series' file, so the file is what is built. go-tools' `track: kernel` followed a series by its X.Y and would have stopped at 7.4-rc5 (spin-stack/go-tools#142). *Status:* in place; a new kernel for every guest's next boot, checkpoints keep resuming.
