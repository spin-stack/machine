The 50 ms bound is the bench's, set for the release's QEMU on c8id hosts (#423). #653 ran the same test with the ASan and UBSan QEMU on the KVM fleet and set no bound for it. *Read* from every Sanitize boots job that reached the test, 2026-11-23 to 26, 49 runs of 3 saves, main and pull requests. The busy-disk guest read 29.8-45.7 ms p50 on 8th-generation hosts (c8i, c8id, m8i, 42 runs) and 41.5-54.7 on 7th-generation ones (c7i, m7i, 7 runs). Six runs read 45 or more, five of them on 7th generation. The slowest of ~600 saves was 60.9 ms, the writer without the busy disk on a c7i. The bench's release QEMU (release.yml's `pause` and lab `check:checkpoint-pause`, 18 runs, c8id) read 17.1-23.2 ms p50. Per save on the bench, the busy disk moved nothing: 18.5 ms p50 with and without it, and the stop after QEMU's downtime 10.7 against 10.6 ms (180 saves each). Under ASan the busy disk added ~2 ms p50 (33.4 against 31.9 on 8th generation, 46.3 against 44.1 on 7th). What ASan's QEMU on a 7th-generation host adds is CPU: more RAM left at the stop (25-44 MiB p50 against 8-11), a longer QEMU downtime (26-29 ms against 18) and a longer save (692 ms total against 611). A c8id host with an instance store read the same as a c8i on EBS, so the disk is not it either. Not #444: that is the short-of-memory guest, which Sanitize skips, and it waits on dirty-page throttling that the bench's busy disk alone never reached. *Built:* the test reads whether the QEMU it times calls `__asan_init` and holds that one under 80 ms (`sanitizedPauseBound`), the slowest median and a third. The bench's 50 stays. *Checked:* Sanitize dispatched on the branch passed, on a c8i, the busy-disk guest at 35.00 ms p50 (run 45896592272).
