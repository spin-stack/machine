A runner hosts about 20 workspaces, and spin has to hold back the one that saturates the shared disk, per disk and while it runs, without the guest learning of it. The prototype said every disk place sits behind a throttle node, so a limit would be one `qom-set` on its group. *Checked* in `machine/spec.go`: every place's node is a throttle filter, but all of them are in one group, `places`, and a group shares its limit among its members, so a limit there would hold all of a machine's disks together. A disk attached while the machine runs has no filter at all. A group per place would have changed the command line every machine boots with. *Built:* `QEMU.SetDiskLimit(serial, DiskLimit)` and `QEMU.DiskLimit(serial)`, where `DiskLimit` is bytes and requests a second, read and write, and its zero value is no limit. The command is `block_set_io_throttle`, sent to the backend of the disk's device, whose group is the device's alone and which a bind never replaces. It reaches a place and a hot-plugged disk alike, and is read back from `query-block`. `verify qemu`'s schema check covers both, and refused a misnamed field in each when one was tried. Bursts are left out: QEMU already lets a tenth of a second's worth through at once. The probe reports a held disk as `Limited{DiskReadBytes…}`, its serial in `Device`, from one `query-blockstats` a second, and only while a disk is held through Start's monitor. *Measured* (task boot:disk-limit, laptop KVM, v20261121.01 with this checkout's spin-machine, spin's shape with two disks beside the root, 3 runs): 8 MiB/s held 32 MiB of the guest's direct reads to 3.776-3.777 s, 50 writes a second held 150 direct 4 KiB writes to 2.881 s, and a disk attached at run time read at 8 MiB/s in 3.900-3.901 s. The other disk did the same in 2-6 ms beside each, and the held one read in 2-5 ms once cleared. `SetDiskLimit` took 1.8-5.5 ms. In task boot:pressure a 4 MiB/s limit brought a `Limited` each second with `Used` at 4.19-4.25 MB/s. *Decided:* a checkpoint carries no limit. A resumed machine reads `DiskLimit{}` and runs free until spin sets the limit again, which then holds (same lane). The limit is spin's policy for a neighbour, and a resumed machine may have other neighbours. No bench run: neither goal path sends a command it did not send before. *Status:* in place. That lane's `memlimit` phase fails on this laptop on main as well (#429).
