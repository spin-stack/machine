title: lockdown's floor is integrity, and every machine but an enforcer's runs at confidentiality (#734)
issues: [734, 738, 719]
---
*Why:* shirudo's programs read kernel memory through `bpf_probe_read_kernel`, about 140 `BPF_CORE_READ`s, and lockdown at confidentiality, which the kernel forced, refuses the helper, so they cannot load (#734). A kernel patch letting signed programs keep it was ruled out in the source: the objects that hold the reads are loaded without a signature, and every gen_loader loader calls the helper itself (#734's last comment). The maintainer chose a per-machine level. *Done:* the kernel forces integrity (`CONFIG_LOCK_DOWN_KERNEL_FORCE_INTEGRITY=y`, a fixed point of olddefconfig), the floor no command line goes below, since lockdown only rises (security/lockdown/lockdown.c, `lock_kernel_down`). `machine.Cmdline` raises every guest to confidentiality with `lockdown=confidentiality`, its zero value's choice, so a consumer building its own line keeps today's protection; `Cmdline.LockdownIntegrity` (spin-machine's `--lockdown-integrity`) leaves it out for a guest whose enforcer needs integrity, and a `lockdown=` in `Extra` is refused. The level is the booted guest's and not in the machine's record: a checkpoint resumes the guest it saved. The traceable kernel's swap is integrity to none, and a lab tree booting it passes `--lockdown-integrity` when its spin-machine would add `lockdown=`, and is refused if the line would carry one anyway. `task boot:lockdown` boots one guest of each kind: `none integrity [confidentiality]` by default, `none [integrity] confidentiality` with the choice (laptop, 2026-11-25). It accepts a kernel from before #734 forcing confidentiality until a release carries the new one (#738). *Status:* every workspace keeps confidentiality; a shirudo machine runs at integrity once shirudo boots in one, which needs the TPM (#719).
