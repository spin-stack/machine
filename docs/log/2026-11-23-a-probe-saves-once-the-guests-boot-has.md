Every probe that restores took its checkpoint right after the cold login, while the boot's last jobs still ran, and each restore of that state ran them beside the login it timed. *Decided* (the owner, #578): spin checkpoints an empty workspace, a project's workspace or a prebuild long after its boot, never mid-boot, and restore-first measures that. `bootFinished` now waits, over SSH as the probe's user, for `systemctl is-system-running --wait`, then for `multi-user.target` active with no job queued, then for the user manager's own `is-system-running --wait`. The middle step is there because the manager calls its start finished when its queue first empties, which a `Type=idle` unit starting the rest of the boot (#581) finds. docs/measuring.md, "When a checkpoint is taken", is the definition. restore-first, prestart, restore-together, run-delay and transport wait for it. restore-first records it as `finished`. *Measured* as three rows of one tree, so one run compares the probes (bench, nested, spin's shape and login, v20261123.01 with its own spin-machine, 40 each interleaved, lab 45095349849, branch `exp-save-rows`, not for merge): saved finished against saved at the login, restored login 83.8 → 79.0, −4.9 [−7.3, −3.8], `running` +0.3 [−0.6, +1.4], the state +4.5 MiB [+4.3, +4.9], save −13.5 [−15.2, −12.2]. The boot finished 85.6 ms after the login it used to be saved at. A further 3 s settle moved neither the state (−0.0 [−0.4, +0.3]) nor the restored login (+0.4 [−0.6, +1.3]), so the probe waits for nothing after finished. *What moves:* the restore rows step down ~5 ms at this change, from the probe and not the machine, as with #451. The ladder boots every release with the probe of the run, so a ladder stays comparable within itself. Compare a restore measured before this change only within one run. *Status:* in place.
