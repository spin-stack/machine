A runner hosts ~20 workspaces. The platform has to say which of them is short of CPU, memory or IO, which one causes it, and when QMP is slow, so that an agent can later act on one machine at a time. The machine now owns both ends of a probe. In every guest, `spin-machine-pressure.timer` starts a static sender 10 s after the boot. It runs at Nice 19, on the idle scheduler and IO class, as root, out of the OOM killer's way. It arms PSI triggers (150 ms in 1 s) on the guest's CPU, memory and IO, watches its OOM kills, and writes a line to host vsock port 1032 each time one fires. On the host, `machine.ListenPressure` routes each connection by the CID the kernel names. `StartOptions.Pressure` adds the same triggers on QEMU's cgroup, and times every QMP command against what that command took before. `Process.Usage` reads the counters that say who causes a stall: the cgroup, `query-blockstats`, and the balloon's OOM kills and allocation stalls. A prototype settled the shape first. Guest PSI is blind to the host taking a vCPU, and a fast OOM killed before any trigger fired. Host cgroup PSI tells the two apart, but a trigger with a window under 2 s is root's alone. No QMP event carries pressure, and a QEMU loading a state answers no command, so the timing follows the migration's events. *Observed on real QEMU* (task boot:pressure, laptop, v20261121.01, one vCPU, 1 GiB, QEMU pinned to one core, several runs). Three loops brought guest CPU stalls each second and no host ones. One loop with two host hogs on its core brought host CPU stalls each second, and `query-blockstats` took 536 ms against a 14 ms baseline, a `SlowCommand`. Two readers of the disk, 4 KiB at a time, brought guest IO stalls; 1 MiB reads from one reader stalled the guest only now and then. A working set reread through what a 700 MiB tmpfs left brought guest memory stalls. A stream read once did not, because clean cache is reclaimed without a stall. A 3000 MiB allocation brought `OOMKill{1}`. The lane found two bugs. The sender spun at ~0.8 s of the guest's CPU a second, because a kernfs file polls as changed until it is read again. And the OOM killer took the sender in the very OOM it was there to report. *Measured* on the bench, spin's shape and login, v20261121.01 against the same release with the sender put into its overlays (`--edit pressure`), interleaved. Ordered after multi-user.target, the sender started beside the first login. The first login read +0.5 [−2.6, +6.7] at 20 boots (lab 44921602512) and +2.5 [−2.1, +7.6] at 40 (lab 44924252325). With `Type=idle` it read +6.1 [+2.3, +10.0] (lab 44924755505), because the boot's jobs are done just before the login arrives. sshd accepting to the login read +2.6, +3.3 and +2.9 in those three runs, each excluding 0. Started by the timer, the first login read −0.5 [−3.6, +2.9] and accept-to-login −0.5 [−1.8, +0.9] (lab 44926664003, 40 boots). The restored login read +0.2 [−3.0, +2.7] evicted and +1.4 [−3.8, +4.7] cached at 20 (lab 44921841077), and +0.3 [−2.5, +3.2] and +1.1 [−3.6, +4.7] at 40 (lab 44923048262), with the sender running in the checkpoint. With the timer it read +1.8 [−2.0, +5.2] evicted and +0.9 [−2.5, +3.4] cached at 40 boots, the sender not yet started when the state was saved (lab 44926917170). *Status:* in place. A guest's first 10 s go unreported. spin follows with one listener and a watch per Start. Its guest supervisor's `POST /v2/memory-pressure` on port 1027 is then deleted in favour of `Stall{Guest, MemoryPressure}`. The actuators are #395 and #396, and the open questions #391-#394.
