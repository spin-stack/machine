Releases come several times a day, and report.yml measures each one once it is published. Until now nothing stopped a consumer from adopting one that measured slower. *Decided:* a withdrawal marks the release and deletes nothing. The release becomes a GitHub prerelease titled "(withdrawn)", with the reason and the issue at the top of its notes. Its record gets `withdrawn`, the page names it, and the newest release not withdrawn becomes GitHub's latest (`releases withdraw`/`restore`, `withdraw.yml`, run only by a person). Assets, `SOURCES`, signatures, provenance, the record and its charts stay, and compat goes on resuming the release's checkpoints, because a withdrawal says nobody should adopt it, not that it does not resume. The next release is measured against the newest release not withdrawn, and its `against` says which. *The rule* (docs/releasing.md, "Withdrawing a release"): either goal number's Δp50 against the release before it, with its interval wholly above 0, or a failed functional check, unless docs/log.md accepts the cost, as #505 did for v20261122.04's +6.8. At 20 boots a side about 1 in 40 flags of each number is noise, so report.yml's `releases flag` opens an issue with the Δs and the commits between the two releases, and a person decides. A prerelease is what the consumers already skip, read 2026-11-23. go-tools' `github-release` track reads GitHub's `/releases/latest`, which is never a prerelease. ship-it's release list leaves prereleases out. Here, `LatestRelease` and the notes' "what changed since" leave them out too. go-tools#139 is the pin already on a release that was then withdrawn, which `versions check` reads as behind an older release. ship-it#45 is spin's proposal, opened at publish, before the withdrawal. #595 is the `pause` job's functional checks, which open no issue yet.
